# 归档流水线算法规范

本文件是 `src/application/archive.rs` 的行为规范：代码按此执行，修改算法时先改本文件。
测试库验证过的规则以本文件为准，不再逐次口头确认。

## 1. 目录角色

根目录由 `LUX_ARCHIVE_ROOT` 指定（默认 `/vol5/1000/docker/lux-test`），其下：

| 目录 | 角色 |
| --- | --- |
| `链接队列/` | 旁挂（Telegram）交接的**链接任务**：每行一个 `*.json` 作业文件；由流水线消费，见 2.1 |
| `转存目录/` | 资源落地第一站；归档阶段把稳定条目移入 `待整理/` |
| `待整理/` | 等待识别整理 |
| `媒体目录/` | 正式库根：`<类型>/<国内|国外>/<年代>/<片名 (年份)>/`；类型 = 电影/电视剧/动画/演唱会/晚会；年代 = `2010s`/`2020s`…（与既有 影视库 目录一致） |
| `失败目录/` | 每次失败一个 `<时间戳>/` 桶，内含 `原因.txt` 与被移动的条目 |
| `重复目录/` | 与库中为同一版本、体积不占优的条目 |
| `洗版目录/` | 被更大版本替换下来的旧包（`<时间戳>-<原目录名>`） |

## 2. 处理流程

```
链接队列 --(每轮消费)--> 115 转存(U11，未实现) --> 转存目录
转存目录 --(稳定≥settle_seconds)--> 待整理 --> 识别(解析+TMDB) --> 判定 --> 媒体目录 / 重复目录 / 洗版目录 / 失败目录
```

0. **链接队列**：`链接队列/` 里的 `*.json` 作业文件先被消费（见 2.1）。这是 Telegram 旁挂
   （`sidecar/telegram/`）把链接交给 Lux 的唯一入口——旁挂不写 `转存目录`，也不写任何媒体目录。
1. **转存监控**：`LUX_ARCHIVE_WATCH_DIRS` 支持**多个来源**（逗号分隔），例如 115 转 115 的落点与
   百度盘的转存落点（都由 CD2 挂载暴露）；所有来源的稳定条目统一搬进 `转存目录/`（重名追加 ` (2)`
   等后缀），随后进入下方流水线。空目录与未稳定条目跳过；跨文件系统（如百度→115）时自动退化为
   复制+删除，速度取决于带宽。
2. **稳定判定**：条目的修改时间早于 `settle_seconds`（默认 5，`LUX_ARCHIVE_SETTLE_SECONDS`）才被认领，避免移动正在写入的包。
3. **归档阶段**：`转存目录` 的条目整体重命名进 `待整理/`（同一文件系统内 rename，零拷贝）。
4. **整理阶段**：对 `待整理/` 的每个条目执行第 3–6 节的识别与判定。
5. **并发**：TMDB 查询按 8 路并发预取（`METADATA_RESOLVE_CONCURRENCY`）；移动与判定按条目名排序**顺序**执行，保证同名多版本（如 PROPER）判定顺序确定。
6. **运行串行化**：轮询与手动触发共用一把全局锁，任一时刻只有一个 run 在写。

## 2.1 链接队列（旁挂交接）

生产方只写、Lux 只读，两边通过一个目录解耦：

| 路径 | 说明 |
| --- | --- |
| `<root>/链接队列/<毫秒时间戳>-<标题 slug>.json` | 一个链接一个作业文件（`0600`），`POST …/archive/ingest` 原子写入（临时文件 + rename） |
| `<root>/链接队列/状态.jsonl` | 追加写（`0600`）的作业审计：每行一条 JSON，含状态与原因 |
| `<root>/链接队列/已处理/` | 已消费的作业文件（保留原件，便于对账；保持 `0600`） |
| `<root>/链接队列/无效/` | 校验失败被隔离的作业文件 |

作业文件字段（`snake_case`；未知字段忽略；`job_id` / `received_at_unix` 由 Lux 赋值，生产方给的 `jobId` 会被忽略）：

```json
{"job_id":"1750000000123-某剧-第二季-4k","url":"https://115.com/s/xxx","title":"某剧 第二季 4K",
 "mode":"上新","source":"telegram","kind":"115","channel":"@chan","message_id":42,
 "size_bytes":25769803776,"captured_at":"2026-10-18T00:00:00+00:00","received_at_unix":1750000000}
```

`job_id` 就是文件名（去掉 `.json`）：毫秒时间戳保证按到达顺序排序，标题 slug 让人一眼看出是哪个资源。
同一毫秒、同一标题的两个链接会撞名，此时**文件名与 `job_id` 一起**加 ` (2)` 后缀（`202` 返回的 `jobId`、
落盘文件名与状态记录三者始终一致）。
`POST` 的 body 只强制 `url`：`title` / `mode` 建议给，其余字段（`source`、`kind`、`channel`、`message_id`、
`size_bytes`、`captured_at`）可选，名字用同一套 `snake_case`。`mode` 只接受
`手动` / `上新` / `追更` / `洗版` / `全量`（与设置里的监听模式同一套），其它值返回 `400`；
队列里手写的非法值按"校验失败"进 `无效/`。

消费规则：

- 只认队列目录**第一层**的 `*.json`（扩展名大小写不敏感，`X.JSON` 也算）；`状态.jsonl`、`已处理/`、`无效/`
  都不是作业；**符号链接不跟随、不算作业**。消费器与 `status.pending_link_jobs` 共用同一个判定函数，
  不会出现"计数说有、消费说没有"。
- URL 只接受 `http(s)://` / `magnet:` / `ed2k://`，长度 ≤ 2048，含空白或控制字符一律拒绝
  （避免把 `file://` 之类交给将来的转存客户端）；并且 scheme 之后必须有非空 host / 目标：
  `https://`、`https:///s/x`、`magnet:?`、`ed2k://|file|` 这类空链接一律判非法。
- 解析失败且文件"仍在写入"（修改时间新于 `settle_seconds`）→ 留到下一轮；否则移入 `无效/`
  并在状态文件记 `invalid`。
- **幂等键 = URL**：同一链接若已在队列里等待、或已在 `状态.jsonl` 里被消费过，ingest 不会
  再写第二个文件，而是返回已有作业并带 `"duplicate": true`。查重与写盘在进程内串行（`Mutex`），
  并发投递同一 URL 只会落一个作业文件。`状态.jsonl` 或队列目录读不出来时返回 `500` 而不是
  "当作没有重复"——宁可拒绝，也不重复交给转存客户端。
- **115 分享链接转存**：配置了 `transfer115.sidecar_base` 时，`115.com/s/<code>` 形式的作业在记账前
  交给 transfer115 侧车（`POST {sidecar}/transfer`），由它用设置文件里的 cookie 登录 115 并转存到
  `<cd2_prefix>/<target_dir>`；结果按 `transferred` / `failed` / `unsupported` 记账并移入 `已处理/`。
  `auth_required`（cookie 失效）与侧车不可达都**不记账、不移文件**：本轮消费中断（`dry_run` 除外），
  作业留在队列，换 cookie 后下一轮重试——只暂停队列阶段，归档流水线其余部分照常跑。
  magnet / ed2k 不走侧车，直接记 `unsupported`（115 云下载是后续切片）。
  未配置 `sidecar_base` 时退回旧行为：记 `needs_115_client`，不产生 `转存目录/` 条目。
- **逐条失败隔离**：消费是 best effort，单条作业写状态或移动失败只记 `failed` 并继续下一条，
  不会中断整轮 `run_once`（否则磁盘满、`已处理/` 撞名会让整个归档永久卡死）。
  每条的步骤是"先写状态、再移动"：状态已写但移动失败的作业下一轮只重试移动，
  `状态.jsonl` 里不会出现第二条记账。
  `已处理/<作业名>` 被同名目录占用视为需要人工处理的异常（记 `failed`、作业留在队列），
  不会偷偷改名绕过；同名文件属于**另一个**作业时才加后缀。
- 状态文件的状态：`transferred`（已转存/已提交）、`failed`（分享失效、接口报错、或非 115 链接的
  `unsupported`）、`needs_115_client`（未配置侧车时的合法作业）、`invalid`（被隔离）。
  每条记录带 `transfer` 字段（转存结果或条目名）与 `reason`，便于排查。
- 日志脱敏：链接只打印 `scheme://host`，magnet 只打印 `magnet:?xt=urn:btih:<前8位>…`；
  完整链接与 `password=` 不进日志。
- 干跑（`dry_run`）只统计与报告，不移动文件、不写状态文件。


## 3. 条目与名称解析

**条目类型**

- 文件：扩展名属于视频集合（mkv/mp4/avi/mov/wmv/flv/ts/m2ts/webm/rmvb/rm/rmp/mpg/mpeg）才处理；否则判失败「不是视频文件」。
- 目录（发布包）：`dir_contains_video` 递归两层检查是否存在视频文件；没有则判失败「目录内没有视频文件」。
- 目录是否为剧集：目录内有 `Season NN` / `S01` 形式的子目录，或文件名含 `SxxEyy` / `第N集`，或名称本身带集标记 → 剧集；否则按电影尝试。

**名称解析**（`parse_media_name`）

1. 剥离开头的发布组标记 `[Group]` / `【字幕组】`。
2. 提取并剥离 `{tmdb-123456}` / `[tmdb=...]` / `tmdb:...` 提示 → 得到 TMDB id（有 id 时跳过标题搜索，直接查详情）。
3. 无中日韩字符时，把 `.`、`_` 归一化为空格（发布名习惯）。
4. 识别年份（1888–2100 的四位数字，可带括号）、季集（`SxxEyy`、`第N集`）。
5. **片名 = 年份标记之前的 token**（发布名结构为 `片名.年份.标签...`），再剔除画质/编码/字幕等噪声 token（1080p、BluRay、x265、国语、中字…）。
6. 标题中的非法路径字符替换为空格；**英文冒号转为全角冒号**（`20:23` → `20：23`）。

## 4. TMDB 匹配算法

**搜索**（`lookup_tmdb`）

- 有 TMDB id 提示：直接查详情，优先剧集段（有剧集线索时）或电影段，另一段兜底。
- 无 id：先按剧集/电影线索决定尝试顺序（集标记或目录集线索 → tv 优先，否则 movie 优先）。
- 每次尝试**同时查 en-US 与显示语言（zh-CN）两份结果并合并**（同一 id 的两条记录都保留：英文本用于匹配发布名，本地化名用于匹配中文名）。

**打分**（`pick_best_result`，仅在得分 > 0 的候选里取最高）

| 条件 | 分值 |
| --- | --- |
| 标题/原名（title/name/original_title/original_name）与解析片名完全一致 | +100 |
| 标题与解析片名互为前缀 | +40 |
| 发行日期年份与解析年份一致 | +50 |

**详情与年份回退链**（`enrich_details` + `tmdb_match_from`）

1. 详情接口的 `release_date`（电影）/ `first_air_date`（剧集）。
2. 搜索结果的同名字段。
3. 电影的**最早发行日期**（`/movie/{id}/release_dates`，仅取首映/公映类型 1–3）。
4. 剧集**最早一季的播出日期**（详情里的 `seasons[].air_date`）。
5. 剧集 `last_air_date`。
6. 剧集第 1 季接口的 `air_date`。
7. 以上都无 → `未知年份`（用来命名片名目录）；目录层落在 `未知年代`（并在日志留痕）。

**国内/国外（按发行地区）**

- 电影：`/movie/{id}/release_dates` 中**最早的首映/公映日期所在国家**；CN/HK/TW/MO → `国内`，否则 `国外`。
- 剧集：TMDB 无按国家的剧集发行日期 → 用 `origin_country`（首播国），CN/HK/TW/MO → `国内`。
- 无发行数据时回退：制作国 → 原语言（zh/cn/yue）。

**类型板块**

- 类型来自 TMDB 详情 `genres`（本地化名）：含「综艺」→ `综艺`；含「动画」→ `动画`；否则 `电影` / `电视剧`。
- 目录层级 = `媒体目录/<类型>/<国内|国外>/<年代>/<片名 (年份)>`，类型、地区、年代分三级目录；
  年代 = 片名年份所在的十年（`2024` → `2020s`，`2010` → `2010s`），无年份 → `未知年代`；
  这是为了与用户既有 `影视库/媒体目录` 的 `地区/年代` 结构保持一致；
  例外：`晚会` 不分国内国外（`媒体目录/晚会/<年代>/<片名 (年份)>`），因为开幕式、阅兵、
  中秋晚会这类重大节目数量很少，国内国外的节目放在一起。

**晚会/演唱会识别**（不走 TMDB）

- 目录名或文件名带 `{晚会}` / `{演唱会}` 标记 → 强制归入对应类别（优先于关键词）；
- 关键词：含 开幕式/闭幕式/阅兵/晚会/春晚/中秋/元宵/跨年/国庆/联欢/颁奖典礼/庆典 → `晚会`；
  含 演唱会/音乐会/巡演/concert/live → `演唱会`；
- 其余条目照常走 TMDB（电影/电视剧/动画/综艺）；
- 演唱会的国内/国外：标题含中文 → `国内`，否则 → `国外`（这类节目 TMDB 通常没有数据）；
- 晚会/演唱会条目不查 TMDB，直接按名称与年份归档，镜像库写 strm + 最小 NFO（标题/年份）。

## 5. 入库 / 重复 / 洗版判定

目标路径：

- 电影（文件或目录包）：`媒体目录/<类型>/<国内|国外>/<年代>/<片名 (年份)>/`；目录包整体作为该目录（重命名为 `片名 (年份)`），内部文件不重命名。
- 剧集目录包：同上，包内自带的 `Season NN/` 结构原样保留。
- 剧集单集文件：`媒体目录/<类型>/<国内|国外>/<年代>/<片名 (年份)>/Season NN/<原文件名>`。

判定（`decide_existing`，遵循 chill 的 `wash_by_equivalent_size` 语义）：

| 媒体目录中的情况 | 判定 | 动作 |
| --- | --- | --- |
| 目标不存在 | 入库 | 移入目标路径 |
| 存在，新包体积在容差内（`LUX_ARCHIVE_WASH_TOLERANCE`，默认 0.02） | 重复 | 新包移入 `重复目录/`，库中保留 |
| 存在，新包明显更大（超过容差） | 洗版 | 旧包移入 `洗版目录/<时间戳>-<原名>`，新包就位（中途失败则回滚旧包） |
| 存在，新包更小 | 重复 | 新包移入 `重复目录/`，保留大的 |

- `LUX_ARCHIVE_WASH_ENABLED=0` 时关闭洗版，一律判重复。
- 体积比较只读元数据（不读数据），目录包为递归文件大小之和。
- 单次 run 内，前一个条目的目标路径会登记为"已规划"，同名后续条目按同一规则与它比较（dry-run 也这样模拟）。

### 5.1 剧集包按季判定

剧集目录包（解析结果是剧集，且包内**直接子目录**是 `Season NN` / `S01` 这类季目录）**按每个季目录
分别判定**，不再拿整包体积和库中整包比：

| 该季在库中 | 判定 | 动作 |
| --- | --- | --- |
| 不存在 | 入库 | 该季并入 `<片名 (年份)>/Season NN`（季目录规范化为 `Season NN`） |
| 存在，新季体积在容差内，或更小 | 重复 | **该季**移入 `重复目录/<原包名>/Season NN`，库中保留 |
| 存在，新季明显更大（超过容差） | 洗版 | 旧季移入 `洗版目录/<时间戳>-<原包名>-Season NN`，新季就位 |

- 只有真正重复的季进重复目录，其余季照常入库。典型用例：`聊斋 (1996) {tmdb-68678}` 包里有
  Season 01 + Season 02，库里只有 Season 01 → 结果必须是库里有 Season 02、重复目录里只留 Season 01。
- 所有季都重复时才退回整包判定（整包移入 `重复目录/<原包名>`），保持原来的行为。
- 合并后重新生成该剧的本地镜像（§5.5）：已存在的 strm/NFO 不覆盖，只补新季。
- 季处理完后，包里剩下的非季文件（NFO、sample、零散文件）并入片名目录；同名跳过并记 `skipped`。
- 电影包、以及没有季子目录的剧集包（单集文件、整季平铺的包）仍按整包判定。
- 单季失败不回滚其他季：每个季的移动/洗版独立记账，失败的季进 `failed`，其余照常入库。

## 5.5 本地镜像库（strm + NFO + 海报）

115 侧（`媒体目录/`）只放媒体文件；媒体服务器扫描的是**本地镜像库**（`LUX_ARCHIVE_MIRROR_ROOT`，
默认 `/vol5/1000/docker/lux-library`）。镜像与 115 的 `类型/地区/年份/片名` 结构一致，但去掉 `媒体目录/` 这一层，
所以镜像根本身就是可用的媒体库根：

```
<镜像根>/<类型>/<国内|国外>/<年代>/<片名 (年份)>/
  <媒体文件名>.strm          # 内容 = CD2 挂载路径（LUX_ARCHIVE_CD2_MOUNT + LUX_ARCHIVE_CD2_PREFIX + 相对路径）
  <媒体文件名>.nfo           # 电影；剧集为 tvshow.nfo + 每集 <集文件名>.nfo
  poster.jpg / fanart.jpg    # TMDB 海报与背景图
```

- strm 不含任何凭据、不做 302；媒体服务器按 CD2 挂载路径直接读取。
- 写完后目录 0755、文件 0644，保证非 root 的媒体服务器可读。
- 全部幂等：已存在的文件默认不覆盖（回填接口加 `overwrite=true` 才重写）。
- `POST /api/v1/admin/archive/metadata?dry_run=true|false&overwrite=true|false` 为历史条目补生成。
- 失败只记录、不回滚移动（元数据问题不能影响已完成的归档）。

## 5.6 自动入库（按镜像目录自动建库）

代码：`src/application/archive/auto_library.rs`；契约：`docs/handoff/AUTO-LIBRARY.md`。

- **规则**：镜像根的一级子目录 = 一个库。目录名含「电影」→ `MOVIE`，其余 → `SERIES`。
- **动画拆两个库**：`动画/国内` → 库「国内动画」，`动画/国外` → 库「国外动画」（用户决定 2026-10-21）；
  其余类型仍是一个库（地区是库内的目录层）。
- **空目录不建库**：目录下没有任何 strm/nfo 就跳过，避免产生空库。
- **幂等键 = 库根路径**：已注册的根不再建库，因此每个轮询周期跑都不会重复。
- **触发**：① 归档 run 结束时（本轮 organized 非空）；② 启动对账；③ 兜底每 600 秒一次全量对账
  （覆盖外部新增目录、以及进程在两次之间挂掉的情况）。
- **建库后**入队一次全量扫描（走 `ScanJobService`，与手动扫描同一条队列）。
- 建库/挂载/入队失败只记 WARN 并计入日志的 `failed`，不打断归档 run。

## 6. 失败处理

失败原因（写入 `失败目录/<时间戳>/原因.txt` 与日志 WARN，字段含条目名与原因）：

- `无法从文件名解析出片名`
- `TMDB 未找到匹配`（含搜索词与候选数诊断日志）
- `TMDB 查询失败: <错误>`
- `目录内没有视频文件` / `不是视频文件`
- `创建目标目录失败: <错误>` / `移动失败: <错误>`
- `旧版移入洗版目录失败` / `新版移入媒体目录失败`
- `转存→待整理失败: <错误>`

## 7. 性能

- 稳定窗口默认 5 秒（可在设置文件或环境变量中调整）。
- 轮询间隔由 `poll_seconds`（设置文件）或 `LUX_ARCHIVE_POLL_SECONDS` 控制（0/未设 = 关闭，测试环境用 10）。
- TMDB 查询 8 路并发；移动为同文件系统 rename，毫秒级。
- 空跑（无待处理条目）单次 run 约 50 ms。
- lookup（第 9 节）只走到标题层（深度上限 3，`symlink_metadata` 不跟随符号链接），结果缓存 60 秒。
  72,000 条目的合成库实测：release 构建首次约 137 ms、命中缓存约 6 µs（debug 构建首次约 466 ms）。
  代价是归档/洗版完成后最多 60 秒内仍可能返回旧体积。

## 8. 配置项

可调参数和凭证优先来自**设置文件**（`LUX_ARCHIVE_SETTINGS`，默认
`/config/archive-settings.json`，权限 0600，不在 git 仓库内）。文件里缺失的键回退到环境变量，
再缺才用下表默认值。改完下一次 run 即生效，无需重启（轮询间隔在下一轮生效）。

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `LUX_ARCHIVE_SETTINGS` | `/config/archive-settings.json` | 设置文件路径（文件内的键覆盖下面同名的环境变量） |
| `LUX_ARCHIVE_ROOT` | `/vol5/1000/docker/lux-test` | 归档根目录（只由环境变量控制） |
| `LUX_TMDB_API_KEY` | 无 | TMDB v3 API Key（必需） |
| `LUX_TMDB_LANGUAGE` | `zh-CN` | 详情显示语言（搜索同时查 en-US；只由环境变量控制） |
| `LUX_ARCHIVE_POLL_SECONDS` | 0（关闭） | 自动轮询间隔秒数（0–3600） |
| `LUX_ARCHIVE_SETTLE_SECONDS` | 5 | 稳定等待秒数（上限 3600） |
| `LUX_ARCHIVE_WATCH_DIRS` | 空 | 逗号分隔的监听目录（新条目自动搬入 `转存目录/`） |
| `LUX_ARCHIVE_MIRROR_ROOT` | `/vol5/1000/docker/lux-library` | 本地镜像库根（媒体服务器扫描） |
| `LUX_ARCHIVE_CD2_PREFIX` | 空 | 归档根在 CD2 挂载中的相对路径（如 `测试库`） |
| `LUX_ARCHIVE_CD2_MOUNT` | `/media/cloud` | CD2 在媒体服务器容器内的挂载点 |
| `LUX_ARCHIVE_WASH_ENABLED` | 1 | 是否启用洗版 |
| `LUX_ARCHIVE_WASH_TOLERANCE` | 0.02 | 体积容差比例（0–1） |

设置文件结构（`telegram` 段由通知与 Telethon 旁挂共用，凭证读写时打码）：

```json
{
  "tmdb_api_key": "…",
  "watch_dirs": ["/testlib/外部上传"],
  "mirror_root": "/library",
  "cd2_prefix": "测试库",
  "cd2_mount": "/media/cloud",
  "poll_seconds": 10,
  "settle_seconds": 3,
  "wash_enabled": true,
  "wash_tolerance_ratio": 0.02,
  "telegram": {
    "bot_token": "…",
    "chat_id": "…",
    "api_id": "…",
    "api_hash": "…",
    "phone": "…",
    "api_key": "…",
    "notify": ["入库", "整理", "失败"],
    "listen_mode": "上新",
    "listen_channels": ["@channel"],
    "follow_list": ["繁花"]
  }
}
```

`telegram.api_key` 是**旁挂调用 Lux 管理接口**用的密钥（`X-Lux-Api-Key`），与通知 bot 无关；
旁挂优先读它，缺失时才用 `LUX_TG_API_KEY` 环境变量兜底。

保存语义（PUT）：

- 只有**本次真正改动的键**、以及文件里**原本就有的键**会落盘；env 派生值不会被固化进文件
  （否则以后改环境变量就不生效了）。
- 文件里本模块不认识的键（例如旁挂自己的字段、未来版本加的字段）在保存时**原样保留**。
- 越界的数值与类型错误一律返回 400，不会被"钳制成合法值"后偷偷保存。

## 9. 管理接口

- `GET /api/v1/admin/archive/status` — 根目录、各角色目录、链接队列与待消费作业数、TMDB 是否配置、洗版与稳定参数。
- `POST /api/v1/admin/archive/run?dry_run=true|false`（也接受 `1|0`）— 预演/执行一次；返回 `archived_to_pending`、`organized`（含 tmdb_id）、`duplicates`、`washed`、`failed`、`skipped` 清单。
- `POST /api/v1/admin/archive/metadata?dry_run=true|false&overwrite=true|false`（也接受 `1|0`）— 为历史条目补生成镜像元数据。
- `GET /api/v1/admin/archive/settings` — 返回设置文件内容，凭证打码（前 6 位 + 长度），并附
  `known_categories`（通知类别清单，前端据此渲染，新增类别不用改前端）。
- `PUT /api/v1/admin/archive/settings` — 写入设置文件（0600，进程内串行）。缺省的键保留现值；凭证留空表示不修改；
  只落盘本次改动与文件已有的键（见 §8 保存语义）。校验失败返回 400：容差 0–1、轮询/稳定等待 0–3600、
  镜像库与监听目录必须存在、CD2 挂载点必须是绝对路径；只校验本次更新涉及的字段。
  配置优先级：**文件 > 环境变量 > 默认值**（按字段合并，见 §8）。设置文件若是单文件 bind mount，
  `rename` 不可用时退化为原地写（0600）；写入窗口内读到半截 JSON 会回退到环境变量。
- `POST /api/v1/admin/archive/ingest` — 旁挂交接入口。Body `{"url":"…","title":"…","mode":"…"}`（其余字段可选，
  见 2.1）；返回 `202 {"ok":true,"jobId":"…","file":"…","status":"queued","duplicate":false}`。
  202 的 `status` 是**入队态** `queued`：消费者下一轮才写转存结果（`transferred` / `failed` /
  `unsupported`）或 `needs_115_client`；重复投递时响应里的 `transfer` 带上一条作业已记录的结果。
  同一 URL 重复投递时 `duplicate` 为 `true` 且不会再写文件；需要重新投递已消费的链接时，
  body 加 `"force": true`（跳过 URL 幂等检查、重新入队并分配新 jobId）。
  鉴权同管理接口（`X-Lux-Api-Key` 或 `Bearer`），且**先鉴权再解析 body**：未认证一律 401，
  body 非法 400（不是 axum 的 422）；URL / `mode` 非法返回 `400`；
  队列不可写、或查重所需的 `状态.jsonl` / 队列目录读不出来返回 `500`（拒绝而不是重复排队）。
- `GET /api/v1/admin/archive/lookup?title=<标题>` — 洗版模式用：在 `媒体目录/` 的**标题层**找同名条目，
  返回 `{"title":"…","matched":"某剧 第二季 (2024)","size_bytes":123}`，找不到时 `matched`/`size_bytes`
  为 `null`。只读元数据，不读内容；结果缓存 60 秒（见 §7）。

    匹配规则（宁可漏，不可错——错误体积会让洗版把真升级判成重复）：

    - 只匹配标题层（`<类型>/<地区>/<年代>/<片名 (年份)>`，晚会/演唱会是 `<类型>/<年代>/<片名>`）；
      类型、地区、年份这些目录层永不参与匹配（`?title=2024` 不会返回一整年）。
    - 片名按发布名解析后归一化（全角→半角、小写、只留字母数字），年份单独抽出；
      查询与库中片名都带年份时**要求一致**（`某剧 2019` 不匹配 `某剧 (2024)`），只有一边带年份则放行。
    - 3 个字符及更短的标题只做**精确**匹配（`繁花` 不匹配 `繁花似锦`）。
    - 一侧是另一侧的前缀时，多出来的部分只要不是纯数字就当作发布标签/附带季标记放行
      （`4K`、`HDR`、`第二季`…）；纯数字视为续集序号，不匹配（`流浪地球` 不匹配 `流浪地球2`）。
    - 命中多个时取体积最大的那个；目录树不跟随符号链接、深度上限 3 层。

## 10. 已知限制

- **115 转存只做了分享链接**：`115.com/s/<code>` 走 transfer115 侧车；magnet / ed2k 记 `unsupported`
  （115 云下载是后续切片）。侧车与真实 cookie 的端到端验收尚未进行（离线 21 条用例已过）。
- **侧车串行转存**：同一个 115 会话一次只处理一个作业，队列积压时逐个消费。
- **侧车超时**：Lux 侧 `transfer115.timeout_seconds`（默认 120s，上限 600s）到点即中断，
  作业留在队列下一轮重试；115 侧的大分享可能在 Lux 超时后仍在处理，文件落盘后照常被流水线接走。
- 洗版的"库中体积"来自目录名启发式（第 9 节 lookup），不是数据库查询；命中不了的条目在旁挂侧挂起。
- 目录包内部的文件名与结构不改写（保留原始发布文件）。
- TMDB 没有按国家的剧集发行日期，剧集的国内/国外只能按首播国判定。
- TMDB 数据缺失时年份可能落到 `未知年份`（已在日志记录，可人工复核）。
- 空包（无视频）直接判失败进入 `失败目录`，不会留在 `待整理`；补文件后可人工移回 `待整理` 重新处理。
- 链接队列的失败作业留在队列里每轮重试（`status.pending_link_jobs` 里可见，日志有 WARN）；
  若 `已处理/<作业名>` 被同名目录占用，该作业会一直重试，需人工清理后自动恢复。
